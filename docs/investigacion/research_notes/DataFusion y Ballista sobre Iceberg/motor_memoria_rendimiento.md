## 1. Execution model: pull streams, partitions, batch_size, repartitioning, tokio runtimes

### Takeaway
DataFusion uses a pull-based Volcano model on async Rust streams. Parallelism comes from Exchange (`RepartitionExec`), and the number of partitions is `target_partitions` (default 0, meaning the CPU core count). By default it runs everything, including object-store IO, on one tokio runtime. The documented production practice is a dedicated CPU runtime plus an IO runtime, with the object store wrapped so it runs on the IO runtime. Since 49.0.0, cancellation and yielding rely on tokio's cooperative budget. Since 54, Parquet scans are morsel-driven. Since 52, `CoalesceBatchesExec` no longer exists as a separate operator.

### Cited Findings
- `execute()` produces one or more partitions, each a stream of `RecordBatch`. The consumer pulls with `next()`. Batches have "approximately batch_size rows", and pipeline breakers (for example a full sort) "must read their input fully before producing any output" — [docs.rs datafusion](https://docs.rs/datafusion/latest/datafusion/index.html)
- "DataFusion uses the classic “pull” based control flow". "Balanced parallelism is achieved using Volcano style" Exchange operations, implemented by `RepartitionExec` — [docs.rs datafusion](https://docs.rs/datafusion/latest/datafusion/index.html)
- "The number of cores used is determined by the target_partitions configuration setting". DataFusion uses a tokio runtime as its thread pool. "Using the same (default) Runtime is convenient", but it can cause problems under load or with network sources — [docs.rs datafusion](https://docs.rs/datafusion/latest/datafusion/index.html)
- DataFusion avoids `spawn_blocking` for CPU work: "spawn_blocking is designed for blocking IO, not designed CPU bound tasks". Also, "each Stream is responsible for yielding control back to the Runtime" — [docs.rs datafusion](https://docs.rs/datafusion/latest/datafusion/index.html)
- Defaults on `main` (55.x): `datafusion.execution.target_partitions = 0` (cores), `batch_size = 8192`, `coalesce_batches = true`, `planning_concurrency = 0` (cores), `repartition_aggregations/joins/file_scans/windows/sorts = true`, `repartition_file_min_size = 1048576`, `datafusion.optimizer.enable_round_robin_repartition = true`, `subset_repartition_threshold = 4`, `use_row_number_estimates_to_optimize_partitioning = false` — [configs](https://datafusion.apache.org/user-guide/configs.html)
- In 55.0.0, the default `repartition_file_min_size` dropped from 10 MiB to 1 MiB for parallelism on small files (#22439). TPC-H Q22 was reported 68% faster — [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)
- In 54.0.0, `RepartitionExec` coalesces batches before sending them (#22010), for "up to 50% faster" on repartition-heavy queries. The Parquet scan became morsel-driven, with idle threads pulling small units of work, for up to about 2x on skewed scans such as ClickBench (#20529, #21327, #21342, #21351) — [54.0.0 blog](https://datafusion.apache.org/blog/2026/06/12/datafusion-54.0.0)
- In 52.0.0, `CoalesceBatchesExec` was removed, which lets `LIMIT` push through joins — [52.0.0 blog](https://datafusion.apache.org/blog/2026/01/12/datafusion-52.0.0)
- In 55.0.0, `EnforceDistribution` and `EnforceSorting` were unified into an `EnsureRequirements` pass (#21976): 8 TPC-H queries faster, none slower — [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)
- Repartition work: a December 2025 post covers avoiding consecutive repartitions — [blog 2025-12-15](https://datafusion.apache.org/blog/2025/12/15/avoid-consecutive-repartitions)
- Cancellation and yielding: tokio cannot interrupt a `poll_next` that keeps returning `Ready`. DataFusion 49.0.0 made built-in sources take part in tokio's cooperative budget, added an `ExecutionPlan` property, and added an `EnsureCooperative` optimizer rule that inserts `CooperativeExec` above custom sources that don't take part. The `datafusion::physical_plan::coop` module helps custom operators. Dropping the stream cancels the query. Plans without exchanges, such as single-core plans, were the vulnerable case — [cancellation blog, 2025-06-30](https://datafusion.apache.org/blog/2025/06/30/cancellation)
- IO and CPU runtimes: the official `thread_pools` example shows running the plan on a dedicated CPU runtime and sending batches back over a channel. In its production version, it routes object-store HTTP to the IO runtime (`SpawnedReqwestConnector`). Without that, "the HttpStore IO operations will *also* run on the CPU runtime, which will error". A later revision adds a `DedicatedExecutor` with `wrap_object_store_for_io` and `spawn_io` (PRs #14286 and #16331, API possibly changed since) — [thread_pools.rs, branch-50](https://apache.googlesource.com/datafusion/+/refs/heads/branch-50/datafusion-examples/examples/thread_pools.rs); [PR #14286 review](https://go.mail-archive.com/github@datafusion.apache.org/msg55561.html)
- InfluxData (A. Lamb, 2022, updated 2023-10-20): tokio is a good scheduler for CPU-bound work. The problem is sharing one runtime between IO and CPU, because health checks stall and the orchestrator kills the process. Recommendations: yield often (10–100 ms between `.await` points is acceptable), use a separate runtime with lower-priority threads (DedicatedExecutor), and amortize per-task overhead with vectorized batches. Rayon has no async support and maps poorly to pull-based execution — [InfluxData](https://www.influxdata.com/blog/using-rustlangs-async-tokio-runtime-for-cpu-bound-tasks/)

### Inferences
- For ORE, run the Query/Build process with two runtimes: an IO runtime for object store, the Iceberg catalog and gRPC/HTTP, and a CPU runtime for `execute()`. Keep health and readiness on the IO runtime so a heavy query can't stall the Kubernetes probe.
- `target_partitions = cores of the pod (cgroup limit)`, not of the node. With 0, DataFusion takes the core count the process sees. Check that it respects the container's CPU quota (not verified, see Gaps).
- A thread-per-core model has no official support. The ecosystem has bet on work-stealing tokio plus morsel-driven scans (54).

### Gaps
- No primary source was found for a formal "thread-per-core vs tokio" debate in DataFusion in 2025–2026.
- Not verified whether `target_partitions = 0` uses `std::thread::available_parallelism` (which respects cgroups v2 on Linux) or the physical core count.
- The final API of `DedicatedExecutor` in 55.x (whether it moved into a crate or stayed an example) was not confirmed.

## 2. Memory: pools, reservations, DiskManager, spill files, which operators spill

### Takeaway
DataFusion accounts only for **large** consumers through `MemoryReservation` against an `Arc<dyn MemoryPool>` in the `RuntimeEnv`. The default pool is `UnboundedMemoryPool`. `with_memory_limit` builds `TrackConsumersPool(GreedyMemoryPool)` with 5 top consumers. Spilling is **per operator**: the pool has no reclaim callback. As of 55.x, these spill: sort, sort-preserving merge, all aggregation modes, sort-merge join, nested loop join (since 54) and repartition. These do **not** spill: HashJoin (open epic #24768), window, cross join, large-k TopK, symmetric hash join, unnest and recursive queries. You can't change the limit of a built-in pool at runtime, but the trait is public and a custom pool can do it.

### Cited Findings
**Pool API (datafusion-execution 55.2.0)**
- Pools: `GreedyMemoryPool` (first-come first-served limit), `FairSpillPool` (each spillable reservation gets `(pool_size - unspillable_memory) / num_spillable_reservations`), `TrackConsumersPool` (wraps another pool and tracks top consumers), `UnboundedMemoryPool` (no limit) and `PeakRecordingPool` (records the peak of `reserved`). There is also `MemoryConsumerMetrics` — [docs.rs memory_pool](https://docs.rs/datafusion-execution/latest/datafusion_execution/memory_pool/index.html)
- `MemoryPool` trait (`Any + Send + Sync + Debug + Display`): `name`, `register`, `unregister`, `grow` (infallible, "This must always succeed"), `shrink`, `try_grow` ("On error the `allocation` will not be increased in size"), `reserved`, and `memory_limit() -> MemoryLimit {Infinite, Finite(usize), Unknown}` (default `Unknown`; custom pools should implement it) — [mod.rs source](https://docs.rs/datafusion-execution/latest/src/datafusion_execution/memory_pool/mod.rs.html)
- `MemoryConsumer { name, can_spill, id }` with `with_can_spill`. `MemoryReservation` has `try_grow`, `grow`, `shrink` (panics if capacity > size), `resize`, `try_resize`, `split` and `free`, and returns its bytes on drop — [mod.rs source](https://docs.rs/datafusion-execution/latest/src/datafusion_execution/memory_pool/mod.rs.html)
- Pragmatic accounting: "Rather than tracking all allocations, DataFusion takes a pragmatic approach". Intermediate streaming memory is not accounted. DataFusion "does NOT track and limit memory used internally by other operators such as `DataSourceExec`". When setting limits, "reserve some overhead (e.g. 10%)" — [mod.rs source](https://docs.rs/datafusion-execution/latest/src/datafusion_execution/memory_pool/mod.rs.html)
- Custom pools are explicitly supported: "You can implement a custom allocation policy by implementing the [`MemoryPool`] trait and configuring a `SessionContext` appropriately" — [mod.rs source](https://docs.rs/datafusion-execution/latest/src/datafusion_execution/memory_pool/mod.rs.html)
- `RuntimeEnvBuilder`: the default pool is `UnboundedMemoryPool`. `with_memory_limit(max_memory, memory_fraction)` creates `pool_size = max_memory * memory_fraction` and "defaults to using [`GreedyMemoryPool`] wrapped in the [`TrackConsumersPool`] with a maximum of 5 consumers". The default disk manager is `DiskManagerBuilder::default().build()`. Methods: `with_memory_pool`, `with_disk_manager_builder`, `with_temp_file_path`, `with_max_temp_directory_size`, `with_max_spill_merge_fan_in`, `with_metadata_cache_limit`, `with_object_list_cache_limit`, `with_object_list_cache_ttl`, `with_file_statistics_cache_limit`, `with_cache_manager` and `with_object_store_registry` — [runtime_env.rs](https://docs.rs/datafusion-execution/latest/src/datafusion_execution/runtime_env.rs.html)

**Runtime and spill configs (`SET`-able)**
- `datafusion.runtime.memory_limit = NULL`, `datafusion.runtime.max_temp_directory_size = 100G`, `datafusion.runtime.temp_directory = NULL`, `datafusion.runtime.metadata_cache_limit = 50M`, `datafusion.runtime.list_files_cache_limit = 1M`, `datafusion.runtime.list_files_cache_ttl = NULL` and `datafusion.runtime.max_spill_merge_fan_in = 0` (unlimited) — [configs](https://datafusion.apache.org/user-guide/configs.html)
- `datafusion.execution.spill_compression = uncompressed` (accepts `lz4_frame` and `zstd`), `sort_spill_reservation_bytes = 10485760` (10 MiB reserved per spillable sort for the merge), `sort_in_place_threshold_bytes = 1048576` and `max_spill_file_size_bytes = 134217728` (128 MiB, then rotate files) — [configs](https://datafusion.apache.org/user-guide/configs.html)
- `spill_compression` arrived in 49.0.0 (enum `SpillCompression {Zstd, Lz4Frame, Uncompressed}`). The spill format is Arrow IPC, and PR #23753 enables `lz4`/`zstd` on `arrow-ipc` and adds an option for the IPC buffer allocation strategy — [upgrade guide 49](https://datafusion.apache.org/library-user-guide/upgrading/49.0.0.html); [docs.rs SpillCompression](https://docs.rs/datafusion-common/54.0.0/datafusion_common/config/enum.SpillCompression.html); [PR #23753](https://github.com/apache/datafusion/pull/23753/files)

**Spill evolution 50 → 55**
- 50.0.0: multi-level merge sorts with spill ("It is now possible to execute almost any sorting query" that used to OOM). The nested loop join was rewritten (up to 5x faster, 99% less memory in a microbenchmark) — [50.0.0 blog](https://datafusion.apache.org/blog/2025/09/29/datafusion-50.0.0)
- 54.0.0: `NestedLoopJoinExec` gained a memory-limited path that spills (#21448), with zero overhead when memory is sufficient. It covers INNER, LEFT, LEFT SEMI, LEFT ANTI and LEFT MARK — [54.0.0 blog](https://datafusion.apache.org/blog/2026/06/12/datafusion-54.0.0)
- 55.0.0: larger-than-memory aggregation (#23657, #23965, #24061, on top of the epic #22710 that splits aggregation into dedicated streams). Re-spill when a merge can't reserve memory (#22945): the largest stream is re-spilled in smaller batches instead of failing. Capped merge fan-in (#23066). A spill-pool lost-wakeup bug was fixed (#23522). **Pluggable spill backends**: the `SpillFile` trait and `TempFileFactory` (#21882, #22230), installed with `DiskManagerBuilder::with_temp_file_factory`; the `object_store_spill.rs` example spills to S3. Multi-column GROUP BY memory dropped 46% for mixed keys (#23523) — [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)

**What spills and what doesn't (audit on 55.1.0, epic #25637, 2026-09-23)**
- Spills: sort, sort-preserving merge, all aggregate modes, sort-merge join, nested loop join (since v54) and repartition — [#25637](https://github.com/apache/datafusion/issues/25637)
- Does not spill: hash join (fails on OOM), window (`WindowAggExec`/`BoundedWindowAggExec`), cross join, TopK (bounded by k, but a large k fails), symmetric hash join, unnest and recursive query — [#25637](https://github.com/apache/datafusion/issues/25637)
- Architectural diagnosis: in DuckDB, spill lives in the buffer manager (eviction "for free"). In Spark, the task memory manager calls each consumer's `spill()`. In DataFusion, `with_can_spill(true)` only marks the consumer and "the pool has no callback to invoke"; each operator handles `ResourcesExhausted` itself. Proposed fixes: #25537 (one spill-replay driver for aggregates) and #21422 (reclaim hooks). Other open items: #20715 (backpressure and spill coordination), #22036 (FairSpillPool penalizes the active operator), #25183 (memory-limit guarantees in external sort) and #15538 (TopK spill) — [#25637](https://github.com/apache/datafusion/issues/25637)
- #22036 (2026-05-06, open bug): `SortExec` registers its consumer during `execute()`, before data flows, so the active operator gets `pool_size / num_spill`, which also counts operators that haven't started. With five stacked sorts, spills were `[3,3,2,2,0]` depending on order. Proposals: hierarchical Velox-style pools (root per query, children per task, pipeline or operator), PR #22035 (SubPool) and PR #22043 — [#22036](https://github.com/apache/datafusion/issues/22036)
- #21422 (2026-04-06, open, no assignee): Comet needs an interface so Spark's task memory manager can ask native operators to reclaim memory. Nothing is designed yet — [#21422](https://github.com/apache/datafusion/issues/21422)
- #22946 (2026-06-14, open): `WindowAggExec` buffers **all** input, concatenates it and evaluates ("buffer all input -> concat all input -> compute all partitions -> emit once"). Proposals: a separate `SpillingWindowAggExec`, or streaming for bounded frames (PoC PR #22356). The plan is to deprecate `BoundedWindowAggExec` in favour of a new streaming implementation — [#22946](https://github.com/apache/datafusion/issues/22946)

**Spilling HashJoin**
- Epic #24768 (2026-08-29, open, assigned to peterxcli): hybrid design (resident buckets plus 16 spilled buckets), behind the flag `enable_hash_join_spilling` (off by default), phase 1 in `Partitioned` mode only (avoids `CollectLeft` unless the build side is provably small). Tasks T0–T11; only T0 (benchmark, PR #24779) has started. Benchmark: a 20M-row join **fails in 0.2 s** under a 300 MB `FairSpillPool`, while `prefer_hash_join=false` (SMJ) finishes in 3.7 s, about 3.5x slower than the in-memory hash join when it fits — [#24768](https://github.com/apache/datafusion/issues/24768)
- Key memory detail: the allocation that fails is usually the hash table (about 19.4 B/row for about 8 B of key), requested in **one `try_grow`** after all batches are already held, so the design reserves explicit headroom. The build consumer isn't registered as spillable, so `FairSpillPool` can't treat it fairly — [#24768](https://github.com/apache/datafusion/issues/24768)
- **Memory accounting leak**: a finished join's hash map stays alive through the dynamic filter **without a reservation**, which left about 10 GiB unaccounted in one workload (fwojciec, Oct 12). jayzhan211 agreed to keep a reservation with the map and track it in a separate issue — [#24768](https://github.com/apache/datafusion/issues/24768)
- 2010YOUY01: spill bugs keep reappearing because "the protocol is underspecified", tests are thin and operator code is convoluted. Recommends refactoring first and then building a separate `SpillingHashJoinStream` behind a flag. alamb (Oct 9) says he lacks review bandwidth — [#24768](https://github.com/apache/datafusion/issues/24768)
- Ballista PR #2108 (andygrove, 2026-07-20): `SpillingHashJoinExec`, inner joins only, Partitioned mode, Arrow IPC to the `DiskManager` when `try_grow` fails (it evicts the largest bucket), recursion with a varied seed, and a clear error for an oversized single key. Configs `ballista.execution.spilling_hash_join.enabled=false` and `...partitions=16`. **Closed by the stale bot without merging on 2026-10-02**, with no human review and no cluster benchmark — [Ballista #2108](https://github.com/apache/datafusion-ballista/pull/2108)

### Inferences
- **Changing the limit at runtime**: no built-in pool exposes a setter, and the limit is fixed at construction. Because `MemoryPool` is a public trait and the `RuntimeEnv` holds `Arc<dyn MemoryPool>`, a custom pool with an `AtomicUsize` limit (checked in `try_grow`) is viable. It should implement `memory_limit()` and wrap `TrackConsumersPool` for error messages. Lowering the limit doesn't take back memory already granted: there is no reclaim (#21422), so the effect only shows on later `try_grow` calls.
- **Per query vs per process**: the pool lives in the `RuntimeEnv`. Sharing one `RuntimeEnv` across sessions gives one per-process pool. A per-query budget needs a `RuntimeEnv` per query (sharing `DiskManager` and caches) or a hierarchical custom pool (root = process, child = query), the Velox model mentioned in #22036. For ORE (C8), a reasonable design is a process root pool equal to the pod limit minus about 10–20% (untracked memory: `DataSourceExec`, Parquet decoding, the hash map retained by the dynamic filter, allocator fragmentation), with child pools per query that admission control can resize.
- **FairSpillPool vs Greedy**: FairSpillPool distributes badly in pipelines of blocking operators (#22036), and HashJoin isn't spillable, so it takes memory that FairSpillPool doesn't count as competing. With concurrent queries, FairSpillPool penalizes everyone equally. Greedy lets the first query consume everything. Neither is a per-query arbiter.
- Until #24768 lands, the only robust defence against hash join OOM is `datafusion.optimizer.prefer_hash_join=false` (SMJ, which spills), at about 3.5x cost when the join fits. Another option is retrying with SMJ after a `ResourcesExhausted`, the approach PR #25217 is exploring ("SMJ fallback") ([#24768](https://github.com/apache/datafusion/issues/24768)).
- The 55 spill-to-object-store backend (`TempFileFactory`) suits pods without large local disks (GKE). Combine it with `spill_compression = lz4_frame` to reduce bytes.

### Gaps
- No official user guide was found on "which pool to choose". The library-user-guide/memory-management.html URL returns 404.
- The exact names of the spill metrics in EXPLAIN ANALYZE (`spill_count`/`spilled_bytes`/`spilled_rows`) were not confirmed in the docs (see section 6).
- Not verified whether the HashJoin dynamic-filter reservation has already been fixed in 55.2.

## 3. Optimizer: rules, statistics, joins, dynamic filters, sort/limit pushdown

### Takeaway
DataFusion has a deliberately basic, mostly heuristic optimizer. There is no full cost model. Join input swapping by statistics is the main lever, and join ordering is syntactic with light reordering (issue #17718). Its big advantage from 50 to 55 is **dynamic filters**: TopK, HashJoin (min/max from 50, hash table contents and `IN` for small builds from 52), MIN/MAX aggregates without GROUP BY (52), through more joins, unions and subqueries (53), and runtime row-group pruning for TopK (55). Sort pushdown and LIMIT pruning add to these.

### Cited Findings
- Join ordering: "DataFusion does not currently have a sophisticated cost based optimizer, but has support for the mechanics of join reordering and statistics". The current approach is syntactic ordering with light reordering, to avoid bad orders. Coordination issue #17718 (alamb) cites TPC-DS and CMU's optd — [mail archive of #17718](https://go.mail-archive.com/github@datafusion.apache.org/msg74133.html); [Optimizing SQL part 1](https://datafusion.apache.org/blog/2025/06/15/optimizing-sql-dataframes-part-one/)
- Optimizer configs: `join_reordering = true` (statistics-driven input swapping), `prefer_hash_join = true`, `hash_join_single_partition_threshold = 4194304` bytes, `hash_join_single_partition_threshold_rows = 131072`, `top_down_join_key_reordering = true`, `allow_symmetric_joins_without_pruning = true`, `prefer_existing_sort = false`, `enable_sort_pushdown = true`, and dynamic filters `enable_dynamic_filter_pushdown`, `enable_topk_dynamic_filter_pushdown`, `enable_join_dynamic_filter_pushdown` and `enable_aggregate_dynamic_filter_pushdown` (all `true`) — [configs](https://datafusion.apache.org/user-guide/configs.html)
- Dynamic filters (blog 2025-09-10): a `DynamicFilterPhysicalExpr` (`Arc<RwLock<..>>`) starts as `true` and is updated during execution. Scans use `generation()`/`snapshot()` to prune rows, row groups and files. Join filters arrived in 50.0.0 (INNER only, min/max). Numbers: Logfire "last K" >10x, ClickBench Q23 up to 22x (with late materialization), a join from 2.5 s to 0.1 s (25x). Without late materialization (`parquet.pushdown_filters`), only row groups or files are pruned — [dynamic filters blog](https://datafusion.apache.org/blog/2025/09/10/dynamic-filters)
- 52.0.0: the HashJoin dynamic filter carries the **hash table contents**, not just min/max. Builds with 20 rows or fewer (configurable) become `IN`. MIN/MAX without GROUP BY gets a filter of the form `l_shipdate < __current_min`. Sort pushdown on pre-sorted data reaches about 30x. The SMJ rewrite gives "three orders of magnitude" in pathological cases, and TPC-H Q21 goes from minutes to milliseconds — [52.0.0 blog](https://datafusion.apache.org/blog/2026/01/12/datafusion-52.0.0)
- 53.0.0: filters and dynamic filters push through more join types and `UnionExec` (#19918, #20145, #20192), through subqueries and both sides of nested anti joins, with nested-field pushdown (`get_field`) into the scan. Null-aware anti join (#20137). LIMIT-aware row-group pruning (#18868). Planning in some benchmarks went from about 4–5 ms to about 100 µs — [53.0.0 blog](https://datafusion.apache.org/blog/2026/04/02/datafusion-53.0.0); [LIMIT pruning blog](https://datafusion.apache.org/blog/2026/03/20/limit-pruning)
- 54.0.0: NDV read from Parquet metadata for equality selectivity, a pluggable `StatisticsRegistry`, better semi/anti cardinality estimates, and files and row groups ordered by statistics (improves TopK early stop). Row groups whose statistics show every row matches skip filter evaluation. Uncorrelated scalar subqueries run as a single operator. LATERAL joins — [54.0.0 blog](https://datafusion.apache.org/blog/2026/06/12/datafusion-54.0.0)
- 55.0.0: runtime row-group pruning for TopK (#22450): `topk_tpch` Q8 is 4.2x faster and the suite drops about 43%. Dynamic filters propagate across network boundaries (#24018, #24068; `ExecutionPlan::apply_expressions`/`dynamic_expressions_produced`), relevant for Ballista. Inner joins become semi joins (#22652), redundant LEFT/RIGHT joins are eliminated (#23566), and conjunctions are reordered by cost (#22343, ClickBench Q21 10–13%). Scalar UDFs can be "strict" (#23148). Chained projections are collapsed (planning 623→155 ms, #22389). CSE'd expressions are no longer re-inlined (#23459) — [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)
- Sort pushdown for almost-sorted data has a dedicated post (2026-07-20). Ordering analysis is covered in the 2025-03-11 post — [sort pushdown](https://datafusion.apache.org/blog/2026/07/20/sort-pushdown); [ordering analysis](https://datafusion.apache.org/blog/2025/03/11/ordering-analysis)
- Parquet configs: `datafusion.execution.parquet.pushdown_filters = false`, `reorder_filters = false`, `schema_force_view_types = true`, `binary_as_string = false`, `metadata_size_hint = 524288`, `bloom_filter_on_read = true`, `max_predicate_cache_size = NULL`. Partial aggregation is skipped with `skip_partial_aggregation_probe_ratio_threshold = 0.8` and `skip_partial_aggregation_probe_rows_threshold = 100000` — [configs](https://datafusion.apache.org/user-guide/configs.html)

### Inferences
- Known weakness against DuckDB: join ordering on many-join queries (TPC-DS), because there is no cost model or DP/greedy enumerator. For Iceberg it matters to provide good statistics (row counts, NDV) through the `TableProvider`, since `join_reordering` depends on them.
- `parquet.pushdown_filters` is still `false` by default, and dynamic filters need it to prune at row level (late materialization). It is a candidate to turn on for selective lake workloads, after measuring.

### Gaps
- No 2026 primary source was found that quantifies DataFusion vs DuckDB on TPC-DS or join ordering.
- The configuration key name for the "20 rows → IN" threshold (52) was not confirmed.

## 4. Hash aggregation, joins, recent work and benchmarks

### Takeaway
DataFusion leads ClickBench on partitioned Parquet: fastest on c7a.metal-48xlarge and second on c6a.4xlarge as of 2026-08-24. In 2024 it was first on c6a.4xlarge, which the team credits to StringView, columnar group storage and skipping partial aggregation. In memory-bounded workloads, third-party tests put it behind DuckDB. There is no rigorous 2026 TPC-H/TPC-DS head-to-head.

### Cited Findings
- 2024-11-18 (DF 43.0.0): fastest on ClickBench Parquet on c6a.4xlarge (16 vCPU, 32 GB), hot run, 100 files of about 140 MB, ahead of DuckDB, chDB and ClickHouse (DuckDB slightly faster cold). More than 30% improvement from DF 34 to 43. Techniques: `StringView`, Parquet pushdown (row groups, page index, bloom), skipping partial aggregation for high cardinality, and columnar multi-column group storage (copies each value once instead of twice) — [ClickBench blog 2024](https://datafusion.apache.org/blog/2024/11/18/datafusion-fastest-single-node-parquet-clickbench)
- 55.0.0: "fastest engine for partitioned Parquet on c7a.metal-48xlarge" and second on c6a.4xlarge (combined metric, 2026-08-24). The blog itself warns that ClickBench covers only part of real workloads and reads local files — [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)
- ClickBench lists a DataFusion partitioned 53.1.0 entry (results dated 2026-03-05) — [ClickBench PR #1257](https://github.com/ClickHouse/ClickBench/pull/1257/files)

In 55: GROUP BY on `FixedSizeBinary` (200M UUIDs 1.13→1.07 s, #23646), `approx_distinct` with 50K groups 1723→17 ms (#22768), and `median` 2.7x (#23954) — [54.0.0 blog](https://datafusion.apache.org/blog/2026/06/12/datafusion-54.0.0); [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)

In 55: semi/anti index alignment, TPC-DS Q15 16% (#22794) — [54.0.0 blog](https://datafusion.apache.org/blog/2026/06/12/datafusion-54.0.0); [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)

## 5. Settings that matter and recommended values for lake workloads

### Takeaway
The defaults favour in-memory performance with no memory limit (`memory_limit = NULL` → `UnboundedMemoryPool`). For a multi-tenant lake service, the levers are: an explicit pool limit with headroom, `temp_directory` and `max_temp_directory_size` on a disk sized for it, `spill_compression`, `target_partitions` equal to the pod's cores, `parquet.pushdown_filters` (after measuring), metadata caches, and `prefer_hash_join` as the escape hatch.

### Cited Findings
- Exact defaults are listed in sections 1–3 — [configs](https://datafusion.apache.org/user-guide/configs.html)
- Benchmarks in the dynamic-filter post use `datafusion.execution.parquet.pushdown_filters`, `reorder_filters` (only applies with pushdown), `target_partitions` and `binary_as_string` (required for ClickBench partitioned) — [dynamic filters blog](https://datafusion.apache.org/blog/2025/09/10/dynamic-filters)
- `datafusion.runtime.metadata_cache_limit` (50.0.0): LRU with 50 MB by default, `0` disables. Point reads 12x faster, and an example `metadata_load_time` drops from about 229 ms to about 229 µs — [50.0.0 blog](https://datafusion.apache.org/blog/2025/09/29/datafusion-50.0.0)
- Best practices for point lookups (2026-10-24) — [point queries](https://datafusion.apache.org/blog/2026/10/24/point-queries)

### Inferences (starting values to measure, not established fact)
- `datafusion.runtime.memory_limit` ≈ 80–90% of the pod limit (the 10% "small allocations" headroom comes from the docs; add more because of the dynamic-filter hash map leak in #24768 and Parquet decoding).
- `datafusion.runtime.temp_directory` on a dedicated volume. `max_temp_directory_size` below that volume's capacity. `spill_compression = lz4_frame` (cheap CPU) or `zstd` when the disk is remote or slow.
- `datafusion.execution.target_partitions` = pod CPU limit; `batch_size` 8192 (raise only after measuring).
- `datafusion.execution.parquet.pushdown_filters = true` and `reorder_filters = true` for selective queries (it is the precondition for dynamic filters pruning by row). Measure, because it is off by default.
- `datafusion.runtime.metadata_cache_limit` raised (hundreds of MB) for Iceberg tables with many files, and `list_files_cache_*` according to snapshot rotation.
- Robust mode: retry a query that fails with `ResourcesExhausted` using `datafusion.optimizer.prefer_hash_join = false`.

### Gaps
- No official "recommended values" guide for lake workloads was found.

## 6. Observability inside the process

### Takeaway
`EXPLAIN ANALYZE` gives per-operator metrics (rows, time, bytes, pruning) with `LEVEL summary|dev` and category filters (`METRICS`). `datafusion-tracing` (unofficial) wraps each node in OpenTelemetry spans. Memory is observed through `TrackConsumersPool` (top consumers in errors), `PeakRecordingPool` and `MemoryConsumerMetrics`.

### Cited Findings
- Common metrics: `output_rows` and `elapsed_compute` (summed across cores). TopK: `row_replacements`. Parquet: `bytes_scanned`, `bytes_processed`, `time_elapsed_opening`, `time_elapsed_scanning_total`. Multi-partition operators: `output_rows_skew`. Pushdown: `page_index_rows_pruned`, `page_index_pages_pruned`, `row_groups_pruned_bloom_filter`, `row_groups_pruned_statistics`, `limit_pruned_row_groups`, `pushdown_rows_matched`, `pushdown_rows_pruned`, and timings `bloom_filter_eval_time`, `statistics_eval_time`, `row_pushdown_eval_time`, `page_index_eval_time` — [explain usage](https://datafusion.apache.org/user-guide/explain-usage.html)
- Formats: `indent` (default), `tree`, `pgjson`, `graphviz`. With ANALYZE, only `indent`/`pgjson`. Options: `LEVEL 'summary'|'dev'`, `SUMMARY`, `METRICS 'rows,bytes,timing,uncategorized'|'all'|'none'`, `TIMING`, `COSTS` (= `datafusion.explain.show_statistics`), and `VERBOSE` (per-partition metrics). The `METRICS` option was added in 55 (#21768) — [explain usage](https://datafusion.apache.org/user-guide/explain-usage.html); [55.0.0 blog](https://datafusion.apache.org/blog/2026/08/25/datafusion-55.0.0)
- `datafusion-tracing` (versions 48–53 on docs.rs, unofficial, not an ASF release): a physical optimizer rule (macros `instrument_with_info_spans!`, `instrument_with_debug_spans`, `instrument_with_trace_spans`, `instrument_rules_with_spans`) wraps nodes in an `InstrumentedExec`. It must go **last** in the rule chain, because other rules downcast nodes. `WorkTableExec` (recursive queries) is not instrumented. Works with any OTel collector — [docs.rs datafusion-tracing](https://docs.rs/datafusion-tracing/latest/datafusion_tracing); [lib.rs 53.0.0](https://docs.rs/crate/datafusion-tracing/latest/source/src/lib.rs)
- Memory: `TrackConsumersPool` (top 5 by default with `with_memory_limit`), `PeakRecordingPool` (high-water mark) and `MemoryConsumerMetrics` (snapshot per consumer) — [docs.rs memory_pool](https://docs.rs/datafusion-execution/latest/datafusion_execution/memory_pool/index.html); [runtime_env.rs](https://docs.rs/datafusion-execution/latest/src/datafusion_execution/runtime_env.rs.html)
- Spill metrics: epic #22946 asks to report "spill count, spilled rows, and spilled bytes" for window. #24768 includes T10 "Metrics and docs" — [#22946](https://github.com/apache/datafusion/issues/22946); [#24768](https://github.com/apache/datafusion/issues/24768)

### Inferences
- For C8, a custom pool (a wrapper over `TrackConsumersPool`) can export `reserved()`, the peak and the top consumers as Prometheus metrics per query or tenant, the signal that is missing today for admission control.

### Gaps
- The explain-usage page doesn't list the exact names of spill metrics (`spill_count`, `spilled_bytes`, `spilled_rows`) or `mem_used`. Confirm in `datafusion-physical-plan` (`SpillMetrics`) before relying on them.
- No `datafusion-tracing` release for 54/55 was found (the latest seen is 53.0.0).
